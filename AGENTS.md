# Working in this collection

Skills live under `skills/<theme>/<skill>/`; `README.md` explains the layout and one loop per theme; `STYLE.md` holds the writing rules for every file and every agent; `decisions/` holds the reasons behind the rules, one file per decision. Rules for editing:

- Read `STYLE.md` before writing a line. English only, no em dashes, no arrows in prose, no filler, sources for every platform claim. An en dash is a numeric range or a quoted product string, nothing else (`decisions/0020`). Steps stay free of years, tool names, and platform facts; a sourced fact stands outside `## Steps`.
- The collection is public. No customer domain, key, analytics id, server path, absolute home path, or workspace under `docs/` is ever committed; a site workspace lives in a private repository per site, and the machines workspace the `dx` and `ops` themes share in one private repository per person.
- `bash scripts/check.sh` runs before every commit and must print `ok`. It checks style, private data, then every offline test and syntax check. Customer names to reject sit in `.check_public.local` (gitignored, one regex per line); an empty file warns locally and fails CI, because a pattern list nobody filled makes that check pass blind.
- Test a script before editing the SKILL.md that calls it; `scripts/check.sh` lists the commands. Scripts stay Python stdlib or bash.
- Once a quarter, run `python3 scripts/sources_age.py` and settle every row it names: re-check the claim against the primary source and move the date, rewrite it as a heuristic, or delete the claim and what rests on it. A dated fact nobody re-checks is the way this collection goes wrong while looking finished.
- The router must not lie: adding, renaming, or changing a sub-skill updates `skills/<theme>/<theme>/SKILL.md` and that theme's tables in `README.md` in the same commit, and bumps `version` in that plugin's manifest with an entry at the top of the changelog beside it. `check.sh` fails on a skill that is missing from either place, on a `jorekai-<theme>:<name>` written in any tracked file that names no directory, and when a version and its changelog's top entry differ. A skill that is designed and not built is named in that router's `## Planned` table, which is the only place a reference may point at nothing (`decisions/0021`). `CHANGELOG.md` and `decisions/` are history and stay exempt.
- A measure counts a cost: one number, one unit from `bytes`, `count`, `percent`, `seconds`, lower is better, zero means the check no longer fires (`decisions/0014`). A script that emits measures answers `--measures` with one `id unit` line per check id, and `check.sh` fails when a unit there is missing from the theme's fixes table. A theme that writes log rows ships a `grade` skill whose `grade.py --namespaces` names the tool behind every namespace; `check.sh` compares that to the fixes table both ways, so no row reaches a verify date with nothing able to recompute it.
- One version and one changelog per plugin (`decisions/0013`). `jorekai-seo` uses `.claude-plugin/plugin.json` and `CHANGELOG.md` at the root; `jorekai-dx` and `jorekai-ops` use `skills/<theme>/.claude-plugin/plugin.json` and `skills/<theme>/CHANGELOG.md`. A change to a shared file bumps nothing.
- Two themes measure a machine, so they share one private workspace: one folder per machine under `machines/<hostname>/`, and one log folder per theme at `log/<theme>/` (`decisions/0015`). Every check id belongs to exactly one theme, named in that theme's `references/fixes.md`, and a theme reads only its own log folder. A theme that adds a namespace adds its rows to that table in the same commit, because `check.sh` derives the namespaces it checks from the table itself.
- A change that can take away the way in (`ssh.*`, `key.*`, `fw.*`, `sudo.*`, `user.*`) passes a second gate before its risk class applies: two independent ways in proved from fresh connections, a backup copy, and a rollback timer cancelled only after a new connection succeeds (`decisions/0016`). A skill that touches those namespaces says so in its steps. A way in counts only with the date a fresh connection proved it: `access_paths` carries `name@YYYY-MM-DD` per entry and an undated one never reaches the check.
- Skill directories carry no theme prefix (`skills/seo/setup`); the plugin supplies it, so the invocation is `/jorekai-seo:setup`; prose refers to skills by that full name. Codex has no such namespace, so `scripts/link.sh` names a link `<theme>-<skill>`.
- Every theme shares the same shapes, which is what let the third one, `ops`, cost no new invention: a findings JSON of `tool`, `target`, `counts`, `items` with dotted check ids, each item carrying `measure` of `value`, `unit`, and `by` per target; a weekly log table whose rows carry a measure, a verify date, and a verdict; an `and-now` that answers `stage`, at most three `now` items, and one `then`; a `SKILL.md` of a thesis line, `## Steps` ending on `Done when`, then `## Rules` or `## Interpretation`; a script that is stdlib only, prints its docstring as `--help`, offers `--json`, and exits 0. Code is duplicated between themes on purpose; only these shapes are shared.
- A new skill is user-invoked (`disable-model-invocation: true` plus `policy.allow_implicit_invocation: false` in `agents/openai.yaml`) unless the agent must reach it on its own; then it gets a model-facing `description` with one trigger per branch. Every skill has `agents/openai.yaml`.
